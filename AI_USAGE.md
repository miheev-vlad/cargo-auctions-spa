# AI_USAGE.md

Этот проект был построен в паре с AI-агентом (Claude). Ниже — честный отчёт о том, что
и как использовалось, что было принято руками, что отклонено и что осталось рискованным.

## Что делалось с AI

- Практически весь код (структура FSD, компоненты, хуки, MSW-моки, Zod-схемы, тесты)
  был написан AI-агентом по моим инструкциям и по содержимому `openapi.auctions.v0.json`.
- AI сам разбил задачу на слои FSD, спроектировал внутреннюю форму MSW-хранилища
  (`AuctionRecord`) как посредника между "плоской" моделью данных и двумя разными
  проекциями схемы — `AuctionListItem` и `AuctionShowResponse`.
- AI написал unit-тесты на чистую логику: парсинг search params, ViewModel-маппер
  списка аукционов и Zod-схему ставки.

## Важный момент по ходу работы: схема OpenAPI

Изначально файл `openapi.auctions.v0.json`, упомянутый в задании как "источник правды",
не был приложен к сообщению с самим заданием. Чтобы не блокироваться, я (AI) сначала
**сам написал условную схему** на основе списка полей прямо из текста задания
(`can_set_bet`, `hide_bets_history`, `hide_points_address_and_contacts`,
`no_view_cargo_price`, типы аукциона Request/Up/Down/FixPrice и т.д.) и реализовал
весь стек поверх неё.

Когда настоящий файл `openapi_auctions_v0.json` был прислан отдельно, весь проект был
**переработан под реальную схему**: другая форма ответа (`main/organizer/route/cargo/
trading/payment`, `page/per_page` вместо `page/page_size`, числовые статусы аукциона,
`status_mobile` для торгового статуса пользователя, `AuctionShowTradingPrice` с
раздельными `with_vat`/`no_vat` полями и т.д.). Это был самый рискованный момент всей
работы — не по сложности, а потому что легко было забыть переписать какой-то один файл
и оставить несостыковку между реальной схемой и UI. Поэтому:

- **Что я проверял особенно внимательно:** после переноса реальной схемы — прогонял
  `npm run build` (полная проверка типов TypeScript) и `npm run test` (28 тестов) после
  **каждого** значимого файла, а не в конце, чтобы несостыковки типов ловились сразу
  на границе, а не в куче правок сразу.
- Отдельно перепроверил вручную семантику `status` и `statuses` в `AuctionListRequest`
  — в реальной схеме это два разных фильтра (торговый статус пользователя vs числовой
  статус аукциона 1–8), а не "одно и то же поле, повторённое два раза", как можно было
  прочитать в тексте задания. Это разрешило исходную двусмысленность формулировки.

## Что было отклонено / упрощено осознанно

- **Не все поля фильтрации из реальной схемы реализованы в UI.** Схема содержит десятки
  фильтров (`weight_from/to`, `volume_from/to`, `body_types[]`, `customer`,
  `customer_ids`, `contractor`, `auction_ids`, `price_per_km_from/to`, `sort`,
  `is_favorite`, `mobile_statuses` и т.д.). В UI реализован ровно минимальный набор,
  явно перечисленный в задании (`cargo_num`, `status`, `statuses`, `auc_type`,
  `load_city`, `unload_city`, диапазон дат погрузки, `is_available`, `is_bidder`,
  диапазон цены) — но с **настоящими** именами и семантикой полей из схемы. Остальные
  фильтры сознательно не строил ради завершения задачи в разумный срок — при
  необходимости их легко добавить: тип `AuctionListRequest` их уже описывает.
- **Города — мок-словарь из 12 городов**, а не реальный справочник/поиск по подстроке.
  Это соответствует формулировке задания ("из мок-словаря городов").
- **`auc_type` и одиночный `status`/`statuses` в UI — выбор одного значения**, хотя API
  принимает массивы. Один выбранный вариант оборачивается в массив из одного элемента
  при построении запроса (см. `searchToListRequest`). Множественный выбор (чекбоксы)
  был бы более точным отражением API, но я отклонил это в пользу более простого и
  предсказуемого для проверки UI — компромисс между полнотой и временем.
- **НДС/без НДС в форме ставки:** `SetBetRequest` в реальной схеме содержит только
  `price` без явного указания "с НДС или без". Я принял решение показывать и отправлять
  цену **с НДС** (это то, что видно как "текущая цена" в детальной карточке), и явно
  подписал поле формы как "Ваша цена (с НДС)", чтобы не создавать двусмысленность.
- **Ранжирование ставок в MSW:** реальная схема не описывает алгоритм определения
  места/победителя — это бизнес-логика бэкенда. Для мока я выбрал "чем меньше цена, тем
  выше место" (условная модель понижающего аукциона) для всех `auc_type`, что является
  упрощением: в реальности `Up`/`Down`/`FixPrice`/`Request` вероятно ранжируются
  по-разному. Это явный риск ниже.
- **AI предлагал** сделать фильтры через React Hook Form (как и форму ставки) для
  единообразия. Я отклонил это: RHF даёт мало преимуществ для панели фильтров без
  сложной кросс-валидации, а сложность синхронизации `defaultValues` с URL при каждой
  навигации была бы выше выигрыша. Простой `useState`-драфт проще для проверяющего.
- **AI предлагал** генерировать TypeScript-типы из OpenAPI-схемы через `openapi-typescript`
  автоматически. Я отклонил автогенерацию (сеть в среде ограничена, и вручную
  прописанные типы легче было бы обсуждать/проверять построчно в этом формате), но
  оставил это как первую рекомендацию по улучшению ниже.

## Что проверялось особенно внимательно

- Соответствие полей во всех местах (`entities/auction/model/types.ts`) реальной схеме —
  построчно сверял вложенность (`main`, `organizer`, `route`/`routes`, `cargo`,
  `trading`, `payment`) для списка и для детальной карточки отдельно, т.к. это два
  разных объекта в схеме (`AuctionListItem` vs `AuctionShowResponse`), не переиспользующих
  структуру напрямую.
- Флаги видимости (`hide_bets_history`, `hide_points_address_and_contacts`,
  `no_view_cargo_price`, `can_set_bet`) — что каждый из них действительно управляет
  соответствующим UI-состоянием (а не просто существует в типе, но не используется).
- Мутация MSW-стора после ставки: что `current_price`, `status_mobile`/`your.bet` и
  список ставок (`place`, `is_win`) реально меняются после `POST /bets`, а не только
  создаётся объект ответа — потому что это явное требование задания.
- Что `page`/`per_page` и структура `{data, meta}` совпадают с реальной схемой, а не
  с придуманным изначально `{items, total, page, page_size}`.

## Риски, которые остались

1. **Ранжирование ставок** — упрощённая модель "меньше цена — выше место" не
   отражает вероятную реальную бизнес-логику по типам аукциона (см. выше).
2. **Не реализованы дополнительные фильтры** схемы (см. список выше) — если ревьюер
   ожидает их наличие, потребуется доработка панели фильтров и `searchToListRequest`.
3. **Формат `sort`** (`Record<string, 'asc'|'desc'>`) описан в типе `AuctionListRequest`,
   но не используется в UI и не реализован в MSW-фильтрации.
4. **Тесты покрывают только чистую логику** (маппер, схемы). Компонentных/интеграционных
   тестов (React Testing Library по факту рендера страниц) нет — по времени сделан выбор
   в пользу более широкого покрытия бизнес-логики вместо глубины по UI-тестам.
5. **Обработка `ProblemDetail` для 401/404/503** реализована только для 404 и 422 в MSW;
   401/503 сценарии не воссозданы и не имеют отдельного UI-сценария (кроме общего
   `ErrorState`).
6. **Ручная синхронизация типов со схемой** (без codegen) — при реальном изменении
   `openapi.auctions.v0.json` типы придётся поддерживать вручную; риск расхождения.

## Что бы улучшил при наличии ещё одного дня

- Подключил бы `openapi-typescript` (или аналог) для автогенерации типов из
  `openapi.auctions.v0.json`, чтобы убрать риск №6 выше.
- Реализовал бы оставшиеся фильтры (вес/объём/тип кузова/цена за км/избранное) и
  множественный выбор для `status`/`statuses`/`auc_type` через чекбоксы.
- Добавил бы component-тесты (React Testing Library) хотя бы для формы ставки
  (успешная отправка, 422 с подсветкой поля) и списка (skeleton → data → empty/error).
- Продумал бы более честную модель ранжирования ставок в зависимости от `auc_type`.
- Добавил бы debounce для текстового поля `cargo_num` в фильтрах вместо кнопки "Применить".
- Настроил бы Playwright/Cypress e2e-сценарий "открыть список → отфильтровать →
  открыть карточку → поставить ставку по прямой ссылке → увидеть обновлённую цену".
